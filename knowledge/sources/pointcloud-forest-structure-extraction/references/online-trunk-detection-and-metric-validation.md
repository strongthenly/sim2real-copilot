# 在线树干检测的失效模式 & 覆盖度指标验证法

本篇讲**另一类**任务：不是"离线从点云提树"，而是**一台机器（无人机/机器人）在线建图、在线检测树干、并据此规划补扫**。
这类系统的检测算法往往短小（自己写的连通域 + 圆拟合），失效模式与离线方法完全不同。

---

## 一、⭐ 头号失效模式：把 3D 点云投影到 2D 平面做连通域 → 超检 10~20 倍

### 典型实现（反面教材）

```python
# 树干带 = 离地 1.0~2.2 m（1.2 m 高）
S = P[(agl >= TRUNK_LO) & (agl <= TRUNK_HI)]
c = np.floor(S[:, :2] / VOX)            # ★★ 只取 x,y —— 丢掉 z！
# 2D 平面 8 连通域 → 每块拟合一个圆 → 一个"树干"
ext = Q.max(0) - Q.min(0)               # ★ 只判【水平】尺寸
if ext.max() > 1.3 or ext.max() < 0.06: continue
```

### 为什么会超检

树干/枝叶/灌木在 **XY 平面**上糊成一片 → 大块因 `ext > 1.3` 被丢弃 → **碎成一堆小块** →
每块都满足 `0.06 <= ext <= 1.3` → **每块拟合一个圆** → 一棵真树干周围散布十几个假"树"。
**⚠️ 点云越密，碎得越厉害** —— 所以在线（稀疏）比离线（全量密集）还"好看"。

### 实测数字（同一份 LAS，同一份代码）

| 喂入方式 | 40×40 m 内检出 | 相对真值 |
|---|---|---|
| 真值（CHM 峰值法） | **99 棵** | 1× |
| 在线（无人机飞了一部分、点云稀疏） | 400 棵 | **4×** |
| **离线（同一份代码，全量密集点云）** | **2170 棵** | **22×** |

**判据：检出数 / 真值数 > 3 ⇒ 先怀疑"2D 投影连通域"，别去调 min/max 尺寸阈值。**
**旁证**：所有"检测点"到真值树的距离中位 2.84 m，而树干半径仅 0.2~0.7 m ⇒ 是**同一棵树被检出多次**，
不是"检出了不存在的物体"。（我一度判成后者，方向错了。）

### 正确做法（按改动量排序）

1. **逐层切片 + 跨层关联**（改动最小，复用现有圆拟合）
   ```
   树干带按 z 分 N 层（如 0.1 m × 12 层）
   → 每层各自 2D 连通 + 圆拟合
   → 相邻层的圆中心距 < 0.25 m 视为同一根
   → 一棵树 = 至少 6 层（竖直延伸 >= 0.6 m）都有对应圆
        ★ 灌木/横枝不可能在 12 层里连续出现
   → 树心 = 各层圆心中位；半径 = 各层半径中位
   ```
2. **3D 连通域 + 竖直性约束**：格改 `(ix,iy,iz)`、邻域改 26 邻；再要求
   竖直跨度 ≥ 0.6 m、上下两半质心 XY 漂移 ≤ 0.3 m。
3. **RANSAC 圆柱拟合**（Schnabel et al. 2007 —— 标准做法，圆柱天然排除灌木）
4. **圆拟合质量门（必做）**：残差 RMS > 0.15·r 直接拒绝。
   ⚠️ 反面教材里常见"拟合失败就退回 `质心 + 最远点距离`" ⇒ **任意散布的点云都能被硬造出一个圆** ✗

### 附带缺陷：地面估计

在线系统常用"**2 m 网格最低点**"当地面（`np.minimum.reduceat`）：
密林里最低点会**偏低** → AGL 偏**大** → "离地 1.0~2.2 m"带**整体上移** → 实际取到**树冠** ✗
⇒ 表现为"覆盖率虚高、且与树干毫无关系"（见下节）。
**修法**：格内 **5% 分位**（抗单点毛刺）+ 3×3 形态学开运算。
标准算法族：**CSF 布料模拟**（`pip install cloth-simulation-filter`、PDAL `filters.csf`）、
**PMF/SMRF**（PDAL `filters.smrf`）、**PTIN**。离线详细做法见 SKILL.md 步骤 2。

## 一.5、🔑🔑 比 2D 投影更根本的陷阱：**锚（真值）本身是坏的**

> **上面那 4 个"正确做法"（逐层切片 / 3D 连通 / 竖直性 / RANSAC 圆柱）我全实现并跑过一遍 ——
> 精度**全都还是 ~10%**，一个都没上去。** 因为真正的瓶颈不在算法里。

### 元判据（背下来，能省掉一整天）

> **N 个【结构上完全不同】的方法，给出【几乎同一个】烂指标 ⇒ 先怀疑【评估】，不要怀疑算法。**
>
> 本例：2D 平面连通 / 3D 体素连通 / 逐层切片跨层关联 / 竖直性+拟合质量门 / RANSAC 圆柱
> 这 5 种方法精度全部落在 **9.3% ~ 10.2%** 这个窄带里 ✗
> ⇒ 算法巧合不可能这么一致 ⇒ **是尺子坏了** ✓

### 坏在哪：CHM 峰值法给的是【树冠中心】，不是【树干位置】

```
锚(trees_v5.csv, CHM 峰值法) 在 LAS 里的严格统计（水平 0.30 m 内、离地 1.0~2.2 m）:
    99 棵中   0 点的 32 棵 (32%)   ✗✗
              点数中位只有 24        ✗✗

检出(428 个) 做同样的统计:
    0 点的只有 12 个 (3%)   ✓✓
    点数中位 370            ✓✓
    90% 都 >= 20 点
```

**⇒ 检出里 90% 真的落在 LAS 的一根树干上；而锚自己 32% 是悬空的。**
**⇒ 算法其实是对的，是【锚】把它系统性地压成了 10%。**

**为什么**：CHM 峰值法（local maxima + watershed）给的是**冠层高度模型上的峰**= 树冠中心；
树干受斜树/偏冠/坡地影响，常偏 1~3 m ⇒ **锚位置的 (x,y) 根本不是树干 (x,y)** ✗
（顺带说明：`crown_r` 中位 3.78 m、树间距 3~5 m ⇒ 树冠互相重叠，
 所以"树冠同轴/上方有树冠"这类判据**毫无区分力** ✗ —— 我给这条也白写了一版。）

### 🔑 验证半径必须有【区分力】——用锚自己反查

```
径向 1.2 m ✗  密林里任何位置 1.2 m 内都能找到树干 → "100% 有树干点" ⇒ 完全没有区分力
径向 0.30 m ✓  只够覆盖"自己脚下这根"（树间距 >= 2 m ⇒ 邻树树干进不来）
```

**自检动作（30 秒，必做）**：**拿锚自己跑一遍你要用的验证判据。**
- 锚自己过不了（本例：32% 不过）⇒ **锚是坏的**（或半径太松）
- **一条判据如果连"真值"都要否掉 1/3，它就不是判据** ✗

### 🔑 顺序不能反：**先建可信的评估（锚 + 指标），再调算法**

本轮的弯路：先花 5 轮改算法 → 指标不动 → 才回头查锚。
正确顺序：
```
1. 建锚（独立来源，且【用严格的空间判据交叉验证过】）
2. 定指标（用 精度/召回/F1，不要只看"检出数对不对"）
3. 小步改算法，每步用同一把尺子量
```
**只比"检出数量"是错的指标** —— 检出 2170 和检出 342 谁对，只有 F1 能回答。

### 锚的合格来源（按可靠性）

| 来源 | 可靠性 | 说明 |
|---|---|---|
| **6 个独立方法交叉一致的树表** | 高 | 见 SKILL.md 的"单木提取两法交叉验证"（峰值法 230 / 树干聚类 187 → 取 187~230） |
| **在 LAS 树干带上做严格空间验证后的检出** | 高 | 水平 0.30 m 内 ≥20 点 ⇒ 直接证明"这里有一根树干" |
| CHM 峰值法单独用 | ✗ 低 | **= 树冠中心，不是树干位置**；32% 悬空 |
| 关卡/场景里合成种植的树 | 中 | 位置精确，但那是"场景真值"≠"点云真值"，坡地上 gz 可能不同步 |

★ 工具链：`_ts_offline.py`（喂 LAS 跑在线算法）· `_ts_sweep.py`（一次载入 + 多组参数扫 F1）
· `_det_check.py`（严格空间验证：0.30 m + 高度带 + ≥20 点，并自动与锚对照出结论）

## 二、⭐⭐ 覆盖度指标验证法（本次最有价值的一步）

**当系统报出一个"覆盖率"数字时，在信任它之前必须做两件事。**

### ① 用**独立、更细**的口径在同一份真值点云上复算，看相关性

```
在线系统报的            : 均值 0.675  中位 0.670
粗口径(复刻系统的12扇区, LAS真值) : 均值 0.199  中位 0.000
细口径(36 θ × 20 z = 720 格)     : 均值 0.068  中位 0.000

在线 vs 粗口径 相关系数 = 0.055   ← ★ 几乎无关 ⇒ 这个指标没有意义
粗口径 vs 细口径 相关系数 = 0.885  ← 两个独立复算自洽 ⇒ 说明问题在"在线"那一侧
```
**判据：相关系数 < 0.3 ⇒ 指标不可信**；同时用"两个独立复算互相自洽"来排除"是我的分析写错了"。

### ② ⭐⭐ 铁证式检验：**按"该树有没有真实树干点"分两组，比覆盖率**

```
有树干点(真值) 156 棵 : 在线报 0.693
无树干点(真值) 324 棵 : 在线报 0.666   ← ★ 两组几乎相同！
```
**物理上有树干点的树与没树干点的"树"，覆盖度不可能一样** ⇒ **说明覆盖率根本不是由树干决定的** ✓
（本例根因：地面偏移导致"树干带"落在树冠上；树冠绕树一圈，粗粒度扇区判据自然全满足。）

**旁证**：这些假树的 `covered_bins` 几乎全是 `111111011111` 这种**满圈** ✗，
且覆盖率**千篇一律卡在 0.67 ≈ 8/12** ✗ —— "满圈 + 数值扎堆"是"在扫树冠"的典型指纹。

### ③ 交付话术

- 说清**口径 + 粒度 + 阈值**（"12 扇区 × 每扇区 ≥2 个体素" 这种粗口径容易虚高）
- 覆盖率**只报上界**：同格枝叶点也算覆盖；严口径要收到"径向 r ± 40%"并加入射角约束
- **按树高/胸径分层报**（矮树的"树干"可能只是灌木）

## 三、⭐⭐ 离线回归台：不改飞机、不跑仿真就能验证在线算法

**核心思路**：在线算法通常被写成一个**独立的、只依赖 numpy 的类**（如 `TreeScanCore`），
所以可以**把 LAS 真实点云直接灌进去**，逐轮迭代，完全离线。

### 做法

```python
sys.path.insert(0, "<算法目录>")
import tree_scan_core as TSC        # 只要它不 import rospy，就能离线跑

core = TSC.TreeScanCore()
core.poly = None
core.add_points(P, bbox)            # P = LAS 装在 (N,3) 的点；bbox 限区域
core.detect()
# → core.trees 每项含 .c(圆心) .r .gz .id
```
**三重对照**（缺一不可）：
1. vs **离线真值树表**（CHM 峰值法 / 树干聚类法）
2. vs **在线系统实际输出**（看两者差多少）
3. **每个检测点的"树干带内点数"**（判断是树干还是树冠）

### 性能与预处理（否则跑不动）

- 算法的连通域常是 **Python 循环** ⇒ 必须**预抽稀**：
  先按 0.10 m 体素去重（`np.unique` on 打包键），实测 7579 万点 → 429 万点
- **实测：429 万点 `detect()` 一轮 5.6 s** ⇒ 足够做参数迭代
- ⚠️ **机载算力必须单独评估**：若算法 `tick()` 每 4 s 调一次 `detect()`，
  在 Jetson 上（按本机 2~4 倍计）会阻塞 ✗ ⇒ 上线前必须
  **抽稀点云 + bbox 限区域 + 拉长间隔**，并**先用"只读影子模式"实测单次耗时**

### 已有合成测试台的局限（重要）

若项目自带一个"合成森林 + 模拟扫描"的自测（如 `test_core.py`），它很有用（可验几何精度、含遮挡判断），
**但它的点云只有树干+地面** ⇒ **复现不出"假树"问题** ✗
（假树来自枝叶/灌木混入，合成台里根本没有这些）
⇒ **必须补一个"喂真实 LAS"的离线回归台**，两者互补。

## 五、两个 numpy 陷阱（本次各撞一次，都与掩膜/打包有关）

### 陷阱 1：掩膜后**没同步重取派生变量** → `operands could not be broadcast`

```python
xs, ys, zs, idx = xs[m], ys[m], zs[m], idx[m]     # 第一次掩膜
zb = zs - TZ[idx]                                  # 由【第一次掩膜后】算的
m2 = (zb >= LO) & (zb <= HI)
xs, ys, zs, idx = xs[m2], ys[m2], zs[m2], idx[m2]  # 第二次掩膜
# ✗ zb 没跟着掩膜 → 长度还是 m.sum()
thin = ...  # (m2.sum(),)
zbin = np.clip(((zb - LO)/(HI-LO)*N_Z)...)         # ★ zb 是 (m.sum(),) → 广播失败
```
```
ValueError: operands could not be broadcast together with shapes (28643,) (332087,)
```
**判据：报错里两个长度一大一小、且其中一个是"上一轮掩膜前的规模" ⇒ 就是漏了同步掩膜。**
**修法：在最后一次掩膜之后**重算所有派生量（`zb = zs - TZ[idx]`），别提前算。
> 同族错误在项目里出现过两次（另一处是"掩膜后未重取 `zmax`"）——这是**值得背下来的模式**。

### 陷阱 2：体素键打包 —— int64 溢出 与 基位冲突

```python
# ✗ 溢出：4e15 × 1e6 ≈ 4e21 >> int64 上限 9.22e18
k = (vx + 1_000_000) * 4_000_000_000_000_000 + (vy + 1_000_000) * 4_000_000 + (vz + 1_000_000)

# ✗ 基位冲突：vy 分量上限 102400 > stride 20000 ⇒ 串位
k = (vx + 100000) * 4_000_000_000 + (vy + 100000) * 20000 + (vz + 100000)

# ✓ 8192 进制：各轴 ±4096 偏移后都落在 stride 内，总和 ~4.4e11 安全
vx = np.floor(xs / VOX).astype(np.int64)      # ±120 m / 0.05 = ±2400
k = (vx + 4096) * 67108864 + (vy + 4096) * 8192 + (vz + 4096)
```
**两条自检**（写完先口算一遍，比 debug 快）：
1. **溢出**：`max(分量) × stride < 9.22e18`
2. **不串位**：**下一轴的偏移后最大值 < 本轴的 stride**
   （即 `(vy+off).max() < 8192` 才能用 `*8192` 给 vz 留位）
