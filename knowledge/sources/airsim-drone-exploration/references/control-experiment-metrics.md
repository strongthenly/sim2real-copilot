# 控制实验的测量口径与统计（停车延迟实验实战提炼）

配套 `references/px4-sitl-experiment-automation.md`（那份讲**怎么把后端跑起来**，这份讲**跑出来的数字怎么才算可信**）。
来源：`px4_brake_lab` 停车延迟实验（0/100/200/300 ms × 0.5/1.0/1.5 m/s，每组 5 次，交错顺序，全部真实飞行）。

**核心纪律：单次试验报一个"停止时间/停止距离"是不可信的 —— 必须先拆口径。**

---

## 1 四事件拆分（可信指标的基础）

| 事件 | 定义 |
|---|---|
| `t_send` | 应用层**发出**零速度设定值（日志事件 `zero_velocity_sent`） |
| `t_decel` | **实际开始减速**：水平速度的平滑导数首次低于 `-0.10 m/s²`（用加速度阈值，别拍脑袋定速度百分比） |
| `t_low` | 水平速度首次低于 `0.10 m/s`（进入低速） |
| `t_stop` | 低速**持续 dwell（0.50 s）** 后确认停稳 |

派生的**可信指标**（相对停车请求）：

```
cmd_latency    = t_decel - t_send    指令→实际响应的滞后（MAVROS 传输 + 飞控速度环）
brake_actual   = t_low   - t_decel   实际减速时长
settle_confirm = t_stop  - t_low     低速→停稳确认（含 dwell）
stop_total     = t_stop  - t_send
```

实测（每档 5 次，单位 s）：

| 延迟 | t_send | t_decel | t_low | t_stop | **指令滞后** | **实际减速** | 低速→停稳 |
|---|---|---|---|---|---|---|---|
| 0 ms | 0.000 | 0.082 | 0.746 | 1.250 | **0.082** | **0.664** | 0.505 |
| 100 ms | 0.111 | 0.198 | 0.863 | 1.368 | **0.087** | **0.665** | 0.505 |
| 200 ms | 0.214 | 0.303 | 0.983 | 1.477 | **0.089** | **0.680** | 0.493 |
| 300 ms | 0.308 | 0.390 | 1.026 | 1.528 | **0.082** | **0.636** | 0.502 |

**三条结论**
1. **`cmd_latency ≈ 82~95 ms，跨延迟档位、跨速度都恒定** —— 这就是"应用层发送时刻 ≠ 电机实际制动时刻"的**量化值**。
   任何引用"发送时刻"的结论都必须注明它比物理制动早约 85 ms。
2. **`brake_actual` 四档一致（0.64~0.68 s）** → 附加延迟**只推迟制动起点，不改变制动能力**（这正是实验想隔离的变量）。
3. ⚠️ **"低速→停稳" = 0.505 s 恰好等于 dwell 阈值** ⇒ 它是**人为确认窗口，不是物理制动时间**。
   多口径汇报时，**物理制动完成时刻看 `t_low`**（0.746/0.863/0.983/1.026 s），别看 `t_stop`。

分解自洽性可验：`总停止 = 附加延迟 + cmd_latency + brake_actual + settle_confirm`
（0 ms: 0+0.082+0.664+0.505=1.251 vs 实测 1.250 ✓；300 ms: 0.308+0.082+0.636+0.502=1.528 vs 1.528 ✓）

**时间对齐质量（先证明"可对齐"，再谈指标）**：`ros_s − pose_stamp` 与 `ros_s − velocity_stamp` 均值均 **≈0.0178 s**、最大 0.048 s；
pose/velocity 墙钟新鲜度 ≈0.019 s（最大 0.052 s）⇒ 位置/速度/事件可对齐到 **1~2 个发布周期**内（与 50 Hz 循环一致）。

## 2 名义延迟 ≠ 实测延迟（50 Hz 量化，必须两个口径都报）

**现象**：名义附加延迟 200 ms，逐次实测"请求→发零"= `0.2130, 0.2190, 0.2040, 0.2160, 0.2190` s → **均值 0.2142 s（+7%）**。

**机理**：延迟判定发生在发布循环的 tick 内，实际发零时刻是**第一个越过 `request + delay` 的帧**
→ 平均多出**半个周期**（50 Hz ⇒ +10 ms），再叠加调度抖动。

**必须做的自洽核对（比"系统固有延迟"这种含糊说法强得多）**：
```
实测延迟窗口位移（trace 梯形积分） = 0.2267 m
窗口均速 × 实测延迟 = 1.0581 × 0.2142 = 0.2266 m      ← 吻合到 0.1 mm
```
位移**分解**方法：`请求后位移 = 延迟窗口位移 + 制动段位移`，用 trace 做梯形积分分别算，残差就是口径误差。

**汇报口径**：名义口径（"设 200 ms 会多跑 0.251 m"）与物理口径（0.2267 m 由实测 0.2142 s 在 1.058 m/s 下产生）**两个都给**。
想更接近名义值：把发布频率提到 100 Hz（量化误差减半）。

## 3 自变量必须用**实测值**，且口径要对

- 名义巡航 1.0 m/s → 实测 **1.058**（一致 **+6%**，0.530/1.057/1.587 vs 0.5/1.0/1.5）⇒ **别把名义值当真实初始条件**。
- **★ 踩过的坑**：用 **CRUISE 全段平均** 当自变量是错的 —— 那段混入了加速过程，导致 1.5 m/s 名义只有 **1.233**（偏低 18%），
  会让拟合式斜率虚高。**正解：取"停车请求前 0.25 s"的平均水平速度**（那才是停车瞬间的初始条件）。
- 教训：**拟合之前先确认自变量口径**，否则 R² 再高也是错的模型。

## 4 标定集 / 验证集 —— 用数据回答"复杂优化器是否必要"

**划分**：交错顺序下天然可切 —— 每档**前 3 次 = 标定集**，**后 2 次 = 验证集**（交错保证先后顺序本身不带档位偏置）。

**结果**（验证集 n=6）：

| 目标量 | 标定集拟合式 | 线性模型 MAE / RMSE | 常数补偿 MAE / RMSE | 提升 |
|---|---|---|---|---|
| 停车距离 | `y = 0.0375 + 0.5203·v` | **13.2 mm / 16.0 mm** | 191.9 mm / 232.4 mm | **约 15×** |
| `t_low` | `y = 0.3124 + 0.3991·v` | **23.3 ms / 30.9 ms** | 149.5 ms / 171.3 ms | **约 6×** |

逐点残差全部在 ±30 mm 内。**结论：简单线性时延补偿已达 mm/ms 级精度，没有证据支持引入更复杂的优化器。**
⚠️ 这个结论**有适用边界**（速度 0.5~1.5 m/s、延迟 0~300 ms、静态空域）；一旦扩展到变速度/变扰动，
**必须用同样的标定/验证划分重新证伪它**，不能当既成事实引用。

## 5 速度扫描与空域扩展

- **逐方向探空域要采样多次取最保守**：AirSim GPU LiDAR 点云有随機性，同一方向两次探测会给出不同最近距离
  （本会话 -Y 方向先得 5.07 m、后得 3.76 m）。→ 每方向 ≥3 次取**最小值**。
- 结果：8 个方向里**只有 ENU 45° 的 6.12 m 能容纳 1.5 m/s**（其余 3.76~5.28 m 全部边际不足）。
- **所需前向距离保守估算** = 最少巡航时长（`min_cruise_s`，本例 2 s）× v + 请求后位移：

| 速度 | 请求后位移（0/200/300 ms） | 全程最坏 |
|---|---|---|
| 0.5 m/s | 0.28 / 0.38 / 0.43 m | 1.28 ~ 1.43 m |
| 1.0 m/s | 0.55 / 0.75 / 0.85 m | 2.55 ~ 2.85 m |
| 1.5 m/s | 0.82 / 1.12 / 1.27 m | **3.82 ~ 4.27 m** |

- ⚠️ **三档速度必须同方向才可比** —— 换方向就等于换实验条件（原 270° 对 1.5 m/s 不足，三档整体迁到 45°）。
- 实测（0 ms，45°）：`停车距离 = 0.0333 + 0.5271·v (R²=0.9909)`、`t_low = 0.3165 + 0.3956·v (R²=0.9491)`；
  斜率 0.527 s = **等效总响应时间**（把渐变减速折算成匀速），**不等于** `cmd_latency + brake_actual`（0.727），别搞混。

## 6 分析脚本自身的缺陷（写统计工具时逐条自查）

1. **表头双重格式化**：`hdr = "%-8s..." % (...)` 之后又 `print(hdr % (...))` → `TypeError: not all arguments converted`。
   模板要**保持未格式化**，表头单独 `print(tmpl % (...))`。
2. **硬编码档位**：汇总/进度里写死 `0ms`/`200ms` 两个计数 → 换成 100/300 的批次全显示 0。
   → 统计键用 **(速度, 延迟) 复合键**并**动态列出**所有出现过的键。
3. **批次串味**：同一 `runs/*.jsonl` 目录下多批并存时，"1.0 m/s" 会把**不同附加延迟**的记录混进同一组。
   → 分析工具必须支持 `--batch-file <具体 jsonl>`。
4. **验证脚本要检查退出码**，不能只查语法：本会话第一版验证只跑 `bash -n` + 正则，**误报 ALL PASS**，
   而 `summarize.py` 其实在运行时崩了。
5. **绘图必须用隔离 venv**：系统 `numpy 1.17.4` 与 matplotlib 不兼容（`ImportError: Matplotlib requires numpy>=1.20`），
   用项目里已备好的绘图 venv 跑，**不要升级全局依赖**。
6. 数值核对要写进工具：把"与已知值比对"（PASS/FAIL）做成脚本的一部分，改完回归一眼看出有没有被改坏。

## 7 批量重复实验的契约（配对公平性）

交错顺序（`0 200 200 0 | 0 200 200 0 | 0 200`，或速度版 `0.5 1.0 1.5 1.5 1.0 0.5 ...`）用来**抵消时间漂移**。
除此之外还有四条硬要求：

1. **★ 每次试验前复位场景（AirSim RPC `reset`）** —— 否则第二次的起点 = 上一次的降落点，
   **两组起点不同就不可作严格配对**（原始需求里明确禁止）。复位必须在**启动 PX4 之前**做（复位会切断既有连接）。
2. **保留全部运行，含失败与异常**：成功 → `runs/<ts>_delayXXX/`；失败 → 单独建
   `runs/<ts>_delayXXX_FAILED_runN/`，内含 `FAIL_REASON.txt`（rc / 是否确认落地 / 耗时）+ 完整 stdout/stderr + 后端日志副本。
   每次运行写一行 `batch_<ts>.jsonl`（**成功与失败都写**）。
3. **轮次间 sleep 3 s** 让上一轮清理落定；**某轮失败不中断后续轮次**。
4. **失败判定看"落地确认"，不看退出码**：`summary.json` 里有 `landed_disarmed` 才算 ok。

**配对公平性核对**（跑完必须做，别只报指标）：
起点 Δ、请求点 Δ、以及**各阶段帧数**。本会话实测：起点 Δ<2 cm、请求点 Δ<5 cm，
且 **BRAKE 阶段帧数两组完全相同（74）**、POST_STOP 相同（112）、DELAY 帧数 0 vs 11（=200 ms × 50 Hz ✓）
⇒ 制动过程本身没变，差异只来自延迟 —— 这才叫"变量被干净隔离"。

## 8 安全判据的设计原则（用户明确纠正过，务必遵守）

- **硬安全约束（碰撞、围栏）在定义上不允许越界**；可以"有界越界"的**只能是任务容差**。
  ⚠️ 曾把研究定位写成"允许学习器有界越界"——这是概念错误，已被用户纠正。写任何"可恢复裕度"类命题时都要区分这两类约束。
- **虚拟边界必须"真正参与在线触发"**：判定要用**飞行中在线可测的量**（当前前向距离 + 在线估的 `d_stop(v)`）
  → 越界就立即发零，**不能事后用日志判定**（事后判定不叫触发）。
- 比较不同安全判据时，这四个指标缺一不可：**越界率**（硬安全）、**越界量**、**边界余量**、**触发提前量**（保守程度）。
- 实现方式：**新写一个 trial 节点**去承载判据比较，**不要改动已有的实验节点**（保护已有数据的可复现性）。
