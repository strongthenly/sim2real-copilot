# 自主探索方案（2026-08-14 设计，未实施）

用户需求：给现有 SUPER 架构加入自主探索算法。背景痛点：odin 雷达范围小（~4.5m）、无全局地图、
撞墙（未知被当自由）。探索正好是解药——探索建图 → 全局地图 → 约束飞行范围（用户已确定后续加全局地图）。

## 核心思路：前沿探索（Frontier）+ 复用现有 FSM（最小侵入）

现有 FSM 已有：规划(PlanFromRest/MINCO) + 避障(A* fallback) + 停车避让(AVOID_WAIT) + 循迹。
缺的只有"下一步去哪"——新增探索模块只做一件事：找探索目标 → 发 goal → 复用一切。

```
新增 exploration_node（独立节点）
  - 订阅 /fsm_node/rog_map/*（地图数据）
  - 提取前沿（已知自由 ↔ 未知 边界格子，聚类成簇）
  - 选目标（最近 + 可达 + 信息增益大的前沿簇）
  - 发布 goal → 现有 waypoint_mission 通道（/waypoint_goal）
        ↓
  现有 FSM（不动）：PlanFromRest → MINCO → 飞到前沿 → 雷达扫新区域 → 地图扩展 → 新前沿 → 循环
```

## 探索循环

1. 前沿提取：地图里"已知自由 ↔ 未知"边界格子（簇）
2. 目标选择：最近的、A* 可达的、信息增益大的前沿簇中心
3. 飞行：FSM 沿 MINCO 飞到前沿（复用现有规划/避障）
4. 到达后：雷达扫新区域 → 地图扩展 → 提取新前沿
5. 终止：无新前沿 / 覆盖达标 / 手动停止

## 与现有配置的兼容性（关键优势）

| 现有机制 | 与探索的配合 |
|---|---|
| `frontend_in_known_free: true` | ✅ 天然配合：前沿就在已知边界，A* 只飞已知区 → 飞到边界 → 扫新区域 → 前进 |
| `AVOID_WAIT` | ✅ 探索途中遇障 → 停车等待 → 恢复 |
| `rog_map frontier_extraction_en` | ✅ 基础设施已有（config.hpp 有开关，实现待确认） |
| `pub_unknown_map_en` | ✅ 未知"雾"可视化 = 探索进度 |

## 实施路线（3 阶段）

- **阶段 1（最小可用，~1-2 天）**：exploration_node 独立 Python 节点
  - 前沿提取：从 inf_occ/unk 话题算前沿（或启用 rog_map 内置 frontier）
  - 目标选择：最近前沿簇中心
  - 发布 goal → 复用 waypoint_mission 通道
  - 验证：室内自动探索建图（不撞墙）
- **阶段 2（全局地图，~1 天）**：探索中累积全局占用图（点云+位姿 → 全局栅格）
  - 全局地图 → 约束飞行范围（解决撞墙根本问题）
  - 配合 frontend_in_known_free=true（边界稳定后轨迹乱跳副作用消失）
- **阶段 3（高效化，~2-3 天）**：信息增益目标选择（选"扫到最多新区域"的前沿而非最近）+ 可选回环闭合

## 关键决策点

1. 探索模块位置：独立 Python 节点（快，推荐）vs 集成 FSM C++（性能）
2. 探索目标通道：复用 waypoint_mission 的 /waypoint_goal（现有）vs 直接调 FSM 接口
3. 室内小空间（2.5m 测试环境）：探索很快完成，主要验证链路通

## 注意

- 雷达范围小 → 探索每步只扫 4.5m，速度慢；室内小空间无碍
- 探索途中同样受碰撞坑影响（frontend/robot_r/膨胀），防撞配置要保持
- 动态点云分割（坑35 FAPP 阶段1）在 odin 不稳定点云上失败——探索建图后可考虑用全局地图做静态背景再试
