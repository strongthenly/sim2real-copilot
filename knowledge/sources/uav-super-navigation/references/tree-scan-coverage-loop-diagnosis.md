# 覆盖扫描"看起来卡住"的诊断法（tree_scan / 覆盖增益型任务通用）

**触发**：日志里反复刷同一批目标（树/扇区/视点），`完成` 计数长时间不动 ⇒ 用户问"为什么卡住"。
**不要**一上来就断言"死循环"或"某个 bug" —— 实测有 **四种**截然不同的真相，判据如下。

---

## 姊妹篇：两个问题要分开问 —— 见 `references/coverage-metric-validation.md`

- **本文**回答：「为什么跑不动 / 完成数不动」 ⇒ 下面四种真相的判据。
- **那篇**回答：「它报出来的**覆盖率数字是不是真的**」 ⇒
  用**真值点云复刻同一判据**逐棵对比 · **冒烟枪判据**（物理上不相交的两组报出同一个覆盖率 ⇒
  指标不是由它声称的东西决定的）· 虚高机制（`ground_at()` 取粗网格最低点 ⇒ 高度带落到树冠 ⇒
  树冠充数）· 指标设计（12 扇区太粗、每格 ≥2 体素太松）· 复算脚本的 numpy 掩码/打包坑。
- **组合用法**：先判「它是否真在推进」（本文），再判「推进出来的数可不可信」（那篇）。
  本次两个结论**同时成立**：确实在全域推进 ✓ 但报出的 67% 严重虚高 ✗。

---

## 判据 1：交叉核对【日志频率】vs【结果文件里的计数列】（最便宜）

多数此类节点会把"尝试次数"落盘（本例 CSV 的 `tries` 列）。

- 日志里**每个目标恰好出现 N 次**、且 CSV 里该目标的 `tries` **正好到上限 N 就再也不出现**
  ⇒ **限次淘汰机制在工作** ✓ 不是死循环，是**正常轮转**。
- 日志里出现次数 **远多于** `tries` ⇒ 才可能是重复发送/死循环。

> 本例：`MAX_TRIES = 2`，日志里树235 的扇区 5/4/3 **各出现恰好 2 次**，CSV `tries` 到 2 后被过滤条件
> `if cov[b] or t.tries[b] >= MAX_TRIES: continue` 命中 ⇒ 之后该树从日志消失（16:57/17:04/17:06 相继消失）✓

**顺带检查**：过滤用的是 `>= MAX_TRIES`，所以 `tries` 达到 MAX 的那一轮**仍是最后一次尝试**，不是 bug。

## 判据 2 ★ 时序算术 —— 不需要任何日志文本（最有力）

把"一轮"的**理论耗时**算出来，与**实测间隔**对比：

```
成功到达一轮 = 飞行(视点距离 / max_vel) + dwell + detect 周期
超时一轮     = goal_timeout + overhead
```

- 实测间隔 ≈ **超时路径**的值（且远离到达路径）
  ⇒ **几乎 100% 的尝试是"飞不到"**，而不是"飞到了但没扫到"。

> 本例：`arrive_r=0.6  goal_timeout=35.0  dwell=2.0`，视点在 2~3 m 外、`max_vel=0.3` ⇒ 到达只需 6~10 s；
> 而日志里"去 X"的间隔稳定 **≈ 48 s** ⇒ 与 `35 s + overhead` 吻合，与 6~10 s 差 5 倍
> ⇒ **判定"几乎全是超时"**，无需依赖那两条 `loginfo/logwarn` 是否出现。

**为什么这条重要**：`loginfo`/`logwarn` 经 stdout 重定向落盘时**可能滞后或丢失**，
凭"日志里没看到'超时'字样"下结论会翻车（本例两条分支的日志一度都看不到，但 `tries` 确实在涨）。

## 判据 3：`tries == 0` 的清单 —— 区分"卡住"与"还没轮到"

统计 `tries` **全 0** 的目标数。**全 0 里必然含"已达标"的**（达标后 `cov[b]` 全 1，直接被 continue，不增 `tries`），
所以要用 `(未达标) AND (tries 全 0)` 才是**真实排队中**的数量。

> 本例：`tries` 全 0 有 266 棵 = 148 棵已达标 + **118 棵未达标但一次没试过** ⇒ 它们在排队，不是卡住。
> 这直接推翻了"被那几棵树卡死"的直觉。

## 判据 4：空间分布 —— "被困局部"还是"全域推进"

取 `tries > 0` 的目标坐标，看范围/标准差。

- 铺满整个作业区 ⇒ **全域推进** ✓（贪心最近 + 边走边服务，本来就是全域铺开）
- 聚成一小簇 ⇒ 可能真被困住

> 本例：`tries>0` 的 214 棵覆盖 x −44.5~45.2 / y −41.2~43.8，标准差 (19.5, 25.3) m ⇒ **全域推进** ✓

## 定位到真因后的典型形态：**"合法性检查" ≠ "可达性检查"**

本例最终根因（三类判据合起来指向它）：

```
视点选择只检查【视点位置本身】：在多边形内 ✓ z 在限高内 ✓ 周围 0.9 m 净空 ✓
        ↓ 缺一条
   【从当前位置能否规划出路径】✗
        ↓
发一个"合法但在树丛后面"的视点 → 规划器 A* NO_PATH → 飞机不动
        ↓
白等 goal_timeout → tries += 1 → 换下一个（同样在树后）→ 再失败
```

**佐证信号**（并行规划器日志）：
```
[A*] Escape path searcher, cannot find path, return.
[ERROR] Escape path search failed with [NO_PATH], force return.
[SUPER] PathSearch for new path failed
```
连**逃生路径**都规划不出来 ⇒ 大概率是**规划器自己的膨胀地图把通路堵死**（膨胀步长/机器人半径偏大），
而不是"目标真的不可达"。**先调膨胀参数，再考虑给选点加可见性检查**。

## ⚠️ 反面教训：别急着用几何把"不可达"解释掉

本例我先假设"细树干 < 体素分辨率 ⇒ 每扇区凑不满 N 个体素 ⇒ 几何上不可能"，并算出
`胸径 < 0.38 m 时 周长/12扇区 < 2×0.05 m 体素`。**看着很自洽，但被数据推翻** ✗：

```
达标(>=83%)  n=148  dbh 中位 0.359
未达标       n=332  dbh 中位 0.443   ← 未达标的反而更粗！
```

**教训**：任何"几何/物理上不可能"的推断，**必须拿达标组 vs 未达标组的分布去验证**。
若两组的解释变量分布**没有区分度甚至反向**，那这个假设就是错的 —— 回去看判据 2/3。

## 优化清单（按性价比，供决策）

| # | 措施 | 效果 | 代价 |
|---|---|---|---|
| 1 | 放宽规划器膨胀：`inflation_step: 2→1` 或 `robot_r: 0.35→0.25` | ★★★ 治本（让 A* 在密林找到路） | 碰撞余量变小 |
| 2 | 降 `goal_timeout`（35→15 s） | ★★ 白等时间直接减半 | 少量"慢但能到"的被误判超时 |
| 3 | 选点加**视线检查**（拿现成的占据体素做射线） | ★★ 跳过注定飞不到的视点 | 需写射线 |
| 4 | 落地为"无进展即放弃"：`tries` 涨但覆盖不变 ⇒ 直接标 MAX_TRIES | ★ 少绕一圈 | 达标率略降 |
| 5 | 视点距离候选加更远的站位（本例只有 1.6/2.2/3.0 m） | ★ 密林近站位全被挡 | 远站位入射角差 |

**报给用户时给"总量 + 剩余时间估算"**（本例 `剩余尝试数 × 每轮实测耗时 ≈ 12.6 小时`），
比只说"在跑"有用得多 —— 用户据此决定"继续 or 收工保成果"。

## 顺带发现的次要 bug 形态（值得回写进被测节点）

- **整秒窗口判定 = 死代码**：`if now - ts > 10 and int(now - ts) % 10 == 0: resend()`
  —— tick 周期 ≠ 1 s 时**几乎永远踩不中**那一整秒。要周期性动作请用 `t_last_send` 时间戳比较。
- **同目标惩罚过小**：`cost = 距离 + (0.0 if same_as_last else 3.0)`，当目标间距 < 惩罚值时
  会在邻近几个目标间来回跳。要么加大惩罚，要么改成"按尝试次数最少优先"。
