# 把真实点云地图（LAS/手持扫描）搬进 AirSim 仿真世界

> 触发场景：用户给一份 `.las`（或 `.ply`/`.pcd`）真实场景点云，说"我想让它在这个地图中跑探索/仿真"。
> 典型来源：留形科技 **odin1** 手持扫描仪 + **Xgrids LixelStudio** 后处理（用户自己的设备）。
> 配套可重跑脚本：`scripts/las_analyze.py`（体检 + 体素抽稀 + AGL 分带 + 出 PLY）。

## 0. 先讲清的核心难点（不先讲这个，方案一定跑偏）

**AirSim / Unreal 的物理世界是【碰撞网格】，点云本身不能碰撞。**
所以"在点云地图里跑仿真"必然要先回答一个问题：
**是把点云【转成几何】搬进 UE4（有物理、会撞树），还是【绕过 UE4】把点云当传感器喂算法（无物理）？**

## 1. 第一步永远是"体检"—— 拿到决策数字再谈方案

```bash
python3 scripts/las_analyze.py <file.las> --voxel 0.5 --ply
```
只依赖 numpy（不需要 laspy / PDAL / open3d / CloudCompare）。

要看的**四个决策数字**：

| 数字 | 决定的决策 |
|---|---|
| 点数 & 0.5 m 体素数 | UE4 用 Instanced Static Mesh 还是先合并大盒子 |
| XY 网格**覆盖率** | 是"整块矩形"还是"采集带"（手持扫描几乎都是后者，影响能不能绕圈飞） |
| Z 直方图 / 地形起伏 | 地面怎么建（Landscape 高度场 vs 平面） |
| ★ **飞行高度带内的体素数** | **要做的碰撞几何规模 = 可行性的唯一硬指标** |

### 本次实例（1225 松树林，2025-12-25 采集）

```
LAS 1.2 · 点格式 3（含 GPS 时间 + RGB）· 生成软件 Xgrids LixelStudio
点数 76,331,398（7633 万）   比例 0.001 m（毫米级）
X -108.2..119.7 (227.9 m)   Y -84.4..117.0 (201.4 m)   Z -27.3..+46.4 (73.7 m)
面积 45,901 m2 = 4.59 公顷   平均密度 1663 点/m2   RGB 100% 有真实颜色
1m 网格覆盖率仅 25%（11,735 / 46,487）  ← 是【采集带】不是整块矩形
分类码全是 class 0（未分类）→ 地面/植被必须自己分
0.5m 体素抽稀 → 291,938 个（抽稀率 0.38%）
```

**AGL（离地高度）剖面 —— 决定可行性的那张表**（逐格局部地面为基准）：
```
AGL  0~ 1 m : 24,528   地面植被 + 树干底
AGL  1~ 2 m : 13,354
AGL  2~ 3 m :  9,345
AGL  3~ 4 m :  9,598
AGL 12~14 m : 18,424   树冠最密层
AGL  22+ m  : 17,554   树冠顶
⇒ 地面 0~3 m 带 = 53,818 个体素；0~4 m 带 = 63,416 个（占 21.7%）
```
**6 万个小方块 → UE4 ISM 毫无压力** ⇒ **方案可行**（这是先体检再谈方案的价值）。

## 2. ⚠️ 两个我踩过的分析陷阱（务必避免）

### 陷阱 1：AGL 用【全局低分位】当"地面" —— 结论会完全错

我第一版写 `band = (z >= percentile(z,1)) & (z <= +6)`，报出"地面以上 6 m 内 13,389 个"。
**这片林子地形起伏 50 m**，所以那个数字实际是"最低洼地带"的体素数，跟"离地高度"毫无关系。

**正确做法**：先算**逐格（1 m）局部地面**（每格最低点 + 迭代中值滤波），
再用每个体素减去它所在格的 `ground` → 得到 AGL。
配套脚本已内置（`ground.npy` + `agl = z - ground[ri, rj]`）。

> 通则：**只要地形有几十米起伏，任何"离地高度/相对地面"的量都必须逐格局部基准**，
> 全局统计量（分位/最小/最大）在这里都是错的。

### 陷阱 2：初版地面估计 + 单木提取不可信（我自己报出过"树高 56.8 m"）

初版用「每格 max_z − 该格 min_z」当冠层高度、`maximum_filter` 找局部极大值提树，结果：
- **提取到"树高 56.8 / 52.2 / 52.0 m"** —— 松树不可能这么高 ⇒ 地面估计在树冠处偏高（激光没穿透树冠，`min_z` 不是地面）
- **`trees.csv` 里所有树的 `ground_z` 都是同一个值 -11.378** ⇒ 地面数组在那些位置被填了同一个中值
- 只提出 **175 棵**（4.6 公顷、25% 覆盖 ≈ 1.15 ha 有效，合理密度应是上千棵）⇒ 局部极大值法**严重漏检**

**要做单木提取（走"程序化种树"路线才需要）必须换正经方法**：
**CSF / 渐进形态学地面滤波** + **CHM 分水岭分割**，别用裸 `maximum_filter`。
并且**先自检**：树高分布合不合理、`ground_z` 是否随位置变化、棵数与密度是否同量级。
> 关键区分：**上面的体素/AGL 统计不受地面估计影响**（那些是按体素坐标直接算的），
> 所以"可行性数字"可以先信，但"树清单"必须重做。

## 3. 三条路线（按"有没有物理"分）

| 路线 | 做法 | 有碰撞？ | 工作量 | 什么时候选 |
|---|---|---|---|---|
| **A. 点云 → UE4 体素几何** | 飞行带体素（0~4 m）→ 方块几何 → UE4 关卡 + 碰撞；全量体素做视觉层；`ground.npy` → Landscape 高度场 | ✅ 真飞真撞 | ~1 天，建议先 40×40 m 试点 | 要物理真实性（撞树、飞控在环） |
| **B. 点云 → 树清单 → UE4 程序化种树** | 单木提取 → 圆柱树干（碰撞）+ 树冠；视觉像树林、渲染轻 | ✅ | 中（依赖单木提取质量） | 树为主、体素太碎时 |
| **C. 跳过 UE4，纯 ROS 点云回放** | 按飞机位置从 LAS 切局部点云 → 发 `/cloud_registered` → 喂 FAST-LIVO2 / rog_map / FUEL / SUPER；位置用运动学积分或 PX4 SITL（忽略碰撞） | ❌ | 半天 | 先验证**算法在真实树林数据上的表现** |

**推荐节奏（风险最低）**：先 C（半天，回答"算法在真树林里表现如何"）
→ 再 A 做 40×40 m 试点跑通"点云→关卡→AirSim"管线 → 最后铺开全图。
理由：A 的管线第一次做必然有坑，先让 C 把科学问题回答掉。

> ⚠️ C 不是"绕过核心组件"：FAST-LIVO2 / FUEL / SUPER 全在跑，只是换了环境载体。
> 但如果用户明确要"飞机真的会撞树"，C 不够 —— 如实说明，别混。

## 5. LAS 解析的几个要点（纯 numpy 即可）

- **头部是固定二进制布局**，按规范 `struct.unpack_from` 手解，**不需要任何库**：
  版本在 24/25、点格式 104、记录长 105、点数 107（LAS 1.4 另有 64 位点数在 247）、
  比例 131/139/147、偏移 155/163/171、范围 179~226。
- **点记录 dtype 用 `reclen` 建，别写死 34**（格式 0=20 / 1=28 / 2=26 / 3=34）。
  用 `np.dtype({'names':…,'formats':…,'offsets':…,'itemsize':reclen})`，
  多出来的尾巴用一个 `_pad` 字段吃掉。
- **数据用 `np.fromfile` / 分块 `read` + `np.frombuffer`**；
  7633 万点 × 34 B = 2.6 GB，**分块 200 万点/批**读完全程约 28 秒（SSD），内存平稳。
- **栅格累计用 `np.minimum.at / np.maximum.at / np.add.at`**（`gi, gj` 索引数组），
  比 Python 循环快几个数量级，内存只有网格大小（228×202 很小）。
- **体素抽稀**：`np.unique` 合并成 int64 键（各轴 + 偏移后打包），
  每块单独 unique 再最终合并，避免一次性持有全量键（7633 万 int64 = 610 MB）。
- **点云上色/出 PLY**：按 Z 上色最直观（蓝低→红高），binary_little_endian PLY 手写头即可。
