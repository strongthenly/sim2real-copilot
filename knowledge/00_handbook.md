## 0. 先读这一页（5 分钟）

这是一台**真实存在的飞机**背后积累下来的运维与算法知识，不是教科书。硬件、拓扑、程序结构、以及大量"看起来像故障、其实是正常现象"的判据，都写在这里。

**三条贯穿全文的元原则**（后面每一层都在用）：

1. **参数值去运行时日志读，别读 launch 文件**。同名 yaml 可能根本没被 include；roslaunch 启动时会逐个打印真正生效的值。这是本项目最高价值的一条诊断纪律。
2. **先分清现象类别再动手**。例："RViz 不显示"必须先分 A 数据没在变 / B 数据在变但不画 / C 根本没东西可画——三者根因毫不重叠，混着查必得出反向结论。
3. **尺子先于算法**。评估指标（覆盖率、精度、真值）不可信时，调参只会把算法调到适配坏尺子。真值必须独立于被评系统，并且冻结。

**机载高度三层语义（最容易混，混了必出"悬停不动"或"撞树"）**：

| 层 | 作用 | 正确范围 | 踩过的坑 |
|---|---|---|---|
| `box_min/max` | 前沿生成的**边界**，必须宽松 | 约 -2.5 ~ 6.0 | 曾被收到 0.3~3.5 -> 假前沿 -> `to visit 0` -> 悬停不动 |

## 3. 各层核心结论速查（不看细节也能用）

### L1 规划与自主飞行

- **两套复飞系统必须先分清**：
  - 系统 A = **Path Replay**（`nx_command_server.py` 内置 daemon，UDP 6003 指令 / HTTP 6004 状态，纯回放、**无避障**，录了什么都飞）
  - 系统 B = **SUPER 航点任务**（`real_flight.launch`：fsm_node + super_to_px4_bridge + waypoint_mission，**有地图/规划/避障**）
  两者混用是最常见的排查走偏原因。
- **QGC 按钮 = UserCmd1/2/3**（走 UDP 6003）。按钮命令用 `&&` 串联是坑：第一环失败会短路，后面 `pkill` 全不执行 -> "停止键无效"。必须改 `;`。且 plink 下 `pkill -f` 会匹配到自身命令行（exit 128）-> 用精确 PID 或 `rosnode kill`。
- **bridge 状态机**：自动起飞悬停 -> CH10 拨杆/按钮触发进入规划飞行。仿真里没有遥控器，必须 `auto_arm` + `auto_offboard`，否则"有规划轨迹但飞机不动"。
- **SUPER 的 `AVOID_WAIT` 是无限重试、永不放弃** -> 目标不可达时永久死锁。治本做法是加"任务级超时放弃"，且**改在 `goal_arbiter.py`（自有组件）里，不碰 SUPER/FUEL 上游源码**。
- **未知区域当自由空间**（`frontend_in_known_free`）是撞墙主因之一；飞机半径 `robot_r` 必须纳入膨胀，否则会因为 `min dis 0.1` 这类小膨胀"擦着树皮过"。

### L2 定位与建图

- **PCD 保存靠 SIGINT 语义**：roscpp 只响应 SIGINT（Ctrl+C），**不响应 SIGTERM**。`kill -TERM` 会让 `savePCD()` 根本没机会执行。
- 保存只在 `while(ros::ok())` 退出后执行一次，条件是 `pcd_save_en && interval < 0`。
- **"关闭慢"通常不是写盘慢**（NVMe 写 341MB 几乎瞬间），而是清理等待链（等 livox 优雅退出）慢。诊断先比日志 mtime 与指令时刻。
- **飞行必须用低算力配置 `MID360_Fly.yaml`**（`dense_map_en=false` + 抽稀 3 倍）；`MID360_Fly_Lidar.yaml` 仅用于专门建图（约 2 倍算力，树林中导致位姿延迟 -> 定点漂移 -> 迫降）。
- **停机脚本绝不触碰 FAST-LIVO2 与 MAVROS**：它们是定位源，断 = 飞不了定点。急停只停探索层与 SUPER。

### L3 机载诊断

- **分层验证**：网络层 -> 设备层 -> SDK/驱动层 -> ROS 话题层，每层独立判据，不跳层。
- **`rostopic hz` 不作数**：话题可以高频发**空消息**（369 Hz 但 `pts=0`）-> 必须取一帧看内容。
- **`Init livox lidars succ` 只代表 SDK 初始化成功，不代表连上雷达**。真正判据是话题有没有、有没有 10 Hz。
- **ping 通但 `ttl=64` + 延迟 <0.1ms = ping 的是自己**（IP 冲突，主机抢占了雷达 IP）；`ttl=255` 才是雷达本体。

### L4 / L5 点云工具与质检

- 判 bag 类型决定走哪条路：标准 bag 用 `rosbags`；**索引损坏/自研 SDK 的非标准 bag 用内置顺序解析器 + 消息字节嗅探**。
- 稠密地图（用 odometry 拼接）与 SLAM 地图质量差异大，**用户主需求是"大小和 bag 差不多 + 要有色"**。
- 质检三层：覆盖 / 全局一致 / 垂直结构；重影检测有正确姿势，姿势不对会大量误报。

### L6 树林与评估（论文内核）

- **单一方法的棵数一定可疑，必须两法交叉验证**。
- **探索目标已从"空间覆盖"改为"物体/树干点云覆盖率"**：
  - ②（度量，即创新目标函数本身）：地面稳健化——格内取 z 的 5% 分位（抗单点毛刺）+ 一轮跨格稳健化（高出 3x3 邻域中位 >3m 的格判为非地面格），`BIN_MIN 2 -> 6`。
  - ③（规划）：视线可达 + 边际覆盖增益 / 飞行代价 + 收尾加权 + 无进展标废。实测路径 -10%、迭代 -25%、达标率 100%。
- **真值必须"两个检测器取并集出候选 -> 人工标注 -> 冻结"**，因为自动提取只有约 50% 可靠。冻结前不跑实验、不调阈值。分母用"可覆盖扇区"，按飞行距离而非视点数比较，多起点配对。
- **在线树干检测失效的头号原因**：2D 投影连通域导致超检 10~20 倍。

### L7 / L8 仿真

- **AirSim 必须跑在 Unreal 上**，WSL 里跑不了；UE4.27 + VS2022 + .NET 桌面开发。
- 点云 -> UE4 的 8 个坑里最关键两条：OBJ 坐标约定、**必须从"AirSim 已跑通的关卡"派生**。
- **PX4 v1.11.3** 在 20.04/gcc9 上免 patch；24.04 + GCC13 才需要 gcc-10 + `static_cast`。
- WSL2 默认 NAT **够不到** Windows 宿主上只监听 127.0.0.1 的 Clash 端口 -> 用 `networkingMode=mirrored`。
- ROS2 apt 源的 `dists/` 用 **Ubuntu 代号**（24.04 = noble），不是 ROS 版本名（jazzy）。

### L9 PX4

- 串级 PID 四层：位置 -> 速度 -> 姿态 -> 角速度，从内到外调。
- **ulg 延迟口径用阶跃法（20-40 ms）**，互相关只用于轴间对比。
- 微空定制固件用**老版 `MPC_XY_*` 命名**，不是 `MC_POS*`。

### L10 集群

七大问题用"目标集合"统一记：一致性=一个点、编队=仿射流形、编队跟踪=时变流形、合围=领导者凸包、编队-合围=分层、分布式优化=`argmin Σf_i`、分布式博弈=纳什均衡集。

三矩阵：**W**（谁跟谁连、连多强）/ **D**（入度 = W 行和，派生量）/ **L = D - W**（连通性算子，`L·1=0`，λ2 = 代数连通度 = 收敛速度，0 特征值重数 = 连通分量数）。

### L11 图传

- 先分清三种：机载直出 / 遥控器透传 / **私有协议**。
- 6000 端口是**私有二进制推流**（`<长度><JPEG>` + 先发 `AUTH:<token>`），不是 RTSP/MJPEG/HTTP。`curl :6000` 报 `Received HTTP/0.9 when not allowed` = **端口活着**，别去查网络。
- 推流已由 systemd 托管（`aircore.target` 四单元），**只用 `systemctl --user restart`**；旧的 `restart_qgc_services.sh` 硬编码旧路径会先杀掉 stream。

### L12 交付

- 先问清是**对外交付**还是**自用部署**，两者流程完全不同。
- **二进制新鲜度**：比源码 mtime 与二进制 mtime，**切勿用 git 提交时间判新旧**。

## 4. 通用操作纪律（跨所有层，违反必踩坑）

### 4.1 远程操作（Windows -> 机载）

| 场景 | 做法 | 坑 |
|---|---|---|
| 交互式 SSH 密码登录 | **用 plink.exe + `-pw`** | Windows OpenSSH 在 PTY 下密码提示会崩（exit `0xC000013A`），且不接受 stdin 密码 |
| 多行脚本 | 落盘 -> base64 -> `base64 -d` 管道送 bash | PowerShell -> cmd -> bash 三层引号地狱；heredoc 会碎 |
| 传文件 | **必须用 pscp** | 用 `cat > file` 会写 0 字节 |
| 需要提权 | 由用户在自己的终端执行 | 远程脚本里的提权命令需要 TTY，不要尝试绕过 |
| plink 执行 | 用 `-m <file>` **不等于**"上传脚本再执行" | 脚本里 `pkill -f` 会自匹配，出现 exit 128 |
| 启停脚本 | **启、停拆成两个 `plink -m`** | 一个脚本里既停止又启动会自杀 |

### 4.2 改代码 / 配置

- 改前**备份**（`cp x x.bak`），逐处贴 diff；多轮改动留一键回退。
- 用 `python3 -c` 改 JSON/YAML，比 heredoc 覆盖更体面且不易破坏格式。
- **改 Python 多行用 `insert` 会让后续行号位移，覆盖掉别的行** -> 用带完整尾部锚点的替换。
- 改 `.rviz` 文本插项的锚点**必须包含前一项的完整尾部**；Marker 项的字段名是 `Marker Topic` 而不是 `Topic`（差一个字）。
- launch 的 XML 注释里连续 `--` 会让 roslaunch 直接拒绝。
- 机上改 C++ 用**锚点三步法**（取原文唯一片段 -> 替换 -> 校验编译）。

### 4.3 诊断纪律

- **别把"正常现象"当故障**：静止时 mm 级坐标抖动；`cloud_registered` 不随无人机动；脚本一停即自动降落（offboard 超时 + `COM_OBL_ACT=1`）；`CMD: Unexpected command 520`；rviz 的 `killing on exit`。
- **`rostopic info` 里的发布者可能是已经死掉的节点**（僵尸注册）。
- **`make` 增量编译：二进制时间戳旧 != 没编译到最新**。catkin_make 判重编看**文件 mtime**，不是 git 提交时间。验证：`find src -name "*.cpp" -newer devel/lib/.../node` 空输出 = 无需重编。
- **同一节点名互相顶掉**：两个 launch 都用 `name="rviz"` 时，后注册的会强制杀掉先注册的（日志 `new node registered with same name`）-> 改名共存。
- **`rostopic echo -n1 <topic>/field` 的输出含 `---` 分隔符**，脚本解析要剔除。

### 4.4 汇报纪律（用户明确要求）

- **分级诚实汇报**：已编写 / 离线通过 / 后端联通 / 实飞通过——四级必须分清，禁止把仿真结果说成实飞结果，禁止用合成数据冒充真实结果。
- 被问"只要确定 X"时**给明确结论 + 证据表**，不要无限排查。
- 报现象类问题**先问清"完全没有"还是"间歇"**——两者根因毫不重叠。
