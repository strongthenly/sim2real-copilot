# 架构说明

## 1. 为什么不是"更多 skill"

模型越强，"按 a→b→c 干活"的流程型指令越多余。仍然有价值的是模型训练数据里没有的东西：这台飞机的拓扑、参数的真实语义、仿真与实机的差异、踩过的坑。因此本仓库的重心是**垂域知识的产生、治理、消费**，以及证明它有效的 **eval**。

## 2. 三层分离

| 层 | 目录 | 回答的问题 |
|---|---|---|
| 知识 | `knowledge/` | 事实是什么？证据在哪？适用于什么范围？ |
| 适配 | `models/` | 怎么让某个模型最好地使用这些知识？ |
| 验证 | `evals/` | 模型用上知识了吗？知识改动变好还是变坏？ |

`trajectories/` 是三者共同的原料。

## 3. 知识怎么评

| 维度 | 方法 |
|---|---|
| 检索 | 回答中是否引用了正确的知识文件（core_prompt 要求写明出处） |
| 利用 | 引用了正确知识但仍答错 → 知识写法问题 |
| 增量 | `--no-knowledge` 对比：差值即知识价值；无增量的知识应精简或删除 |
| 安全 | `critical` 用例一次失败即整轮不合格，不取平均 |
| 泛化 | held-out 集不参与改进，只用于验证 |

## 4. 自我改进（RSI）的边界

```
trajectory → 候选知识 → eval 门槛 → 人工审核 → 入库 → 定期用实机 held-out 复验
```

- 仿真 eval 便宜，每次改动都跑；实机验证昂贵，攒批进行。
- 没有可靠的 eval 门槛，"自我改进"只会变成"自我漂移"。
- 候选知识永远不自动进入 `knowledge/`。

## 5. 安全分级

| 环境 | agent 权限 |
|---|---|
| 仿真（SITL） | 自由操作：启动场景、注入故障、参数扫描 |
| 硬件在环 | 每次操作需确认 |
| 实机 | 只准备参数 diff、飞前检查单、风险说明；由人执行 |
